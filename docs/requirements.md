- 최초 작성 2026-11-27 · 상태: 초안 (팀 검토 전)
- 저장 위치: `docs/requirements.md`

## 한눈에 보기

**이음러닝**은 기업에 AI 교육을 파는 회사다. 분기마다 행사(특강, 세미나)를 열고, 참석자는 신청할 때 궁금한 점(사전 질문)을 남긴다.

**지금의 문제:** 분기마다 참석 기록이 250건쯤 되는데, 담당자가 기억에 의존해 챙기다 보니 연락을 놓치거나 늦는다. 보내는 메일도 모두에게 똑같아서 질문에 답이 되지 않는다. 그러다 보니 계약으로 이어질 수 있던 고객을 놓친다.

**이 시스템이 하는 일:**
1. 행사가 끝나면 참석자마다 **감사 메일**과 **질문에 맞춘 메일**의 초안을 만든다.
2. 질문을 보고 "우리 블로그 글로 답할 수 있는 것", "영업 담당이 직접 상담할 것", "담당자 확인이 필요한 것"으로 나눈다.
3. 사람이 초안을 고치고 승인해야 메일이 나간다. **AI는 초안만 만든다.**
4. 메일에 "○일까지 연락드리겠습니다"라고 약속하면, 담당자가 연락한 뒤 '완료'를 표시하고, 그날까지 완료 표시가 없으면 시스템이 알린다. (실제 통화 여부는 담당자의 표시를 믿는다)
5. 고객이 우리 메일에 회신하면 내용을 분류해서 맞는 담당자에게 넘긴다.

**이 문서는** 위 기능이 정확히 어떻게 동작해야 하는지를 하나씩 적은 목록이다. 팀원이 개발할 때, 그리고 나중에 기능을 고칠 때 이 목록을 기준으로 삼는다.

## 1. 개요

### 1.1 목적
이 문서는 시스템이 **무엇을 해야 하는지** 정한다. 어떻게 만들지(코드)는 다루지 않는다. 팀원과 코딩 AI는 이 문서를 보고 개발하고, 기능을 바꿀 때 여기 적힌 규칙을 깨지 않았는지 확인한다.

### 1.2 범위
| 이번에 하는 것 | 이번에 하지 않는 것 |
|---|---|
| 신청서·설문·회신에 **글로 남은** 질문과 요청에 대한 연락 | 행사장에서 말로만 한 약속 (나중에 추가) |
| 메일 **초안** 만들기, 고치기, 승인하기, 발송 흉내 내기 | 실제 이메일 발송 |
| 영업·담당자에게 넘긴 약속을 지켰는지 확인하기 | 상담 이후 견적·계약 관리 |
| 행사별로 참석자 → 메일 → 영업 연결 수 세기 | 계약까지 이어졌는지 세기 (나중에 추가) |

### 1.3 표 읽는 법
3·4장의 표는 요구사항 하나가 한 줄이다. 칸은 이런 뜻이다.

| 칸 | 뜻 | 예시 |
|---|---|---|
| ID | 요구사항마다 붙인 이름표. 앞 글자는 어느 업무인지 | `REQ-A01` = 행사별 후속 관리(A)의 1번 |
| 요구사항 | 시스템이 해야 하는 일 | 참석자 전원에게 감사 메일 초안을 만든다 |
| 출처 | 누가 원했는지 | `인터뷰 7` = 고객 인터뷰 7번 답변, `팀` = 팀이 분석해서 정함 |
| 우선순위 | 이번에 꼭 해야 하는지 | `필수` 꼭 / `선택` 시간 되면 / `다음` 이번엔 안 함 |
| 검증 기준 | 이렇게 보이면 제대로 된 것 | 행사별 감사 메일 수 = 참석자 수 |
| 상태 | 처음 쓴 건지, 나중에 바뀐 건지 | `최초` / `추가` / `수정` / `삭제` |

- ID 앞 글자: **A** 행사별 후속 관리, **B** 정기 발송(뉴스레터), **C** 고객 회신 처리, **S** 영업 연결, **D** 데이터, **P** 보안·개인정보, **Q** 품질(테스트), **U** 화면 공통
- 출처 약어: `인터뷰 n` 고객 서면 인터뷰 n번 답변, `인터뷰(○○ 문항)` 번호 대신 문항 주제로 적은 것 · `RFP` 과제 요청서 · `06` 고객사 글쓰기 기준 · `07-n` 영업 전달 사례 n번 · `멘토` 11/26 멘토링
- 바꿀 때는 그 줄의 상태와 변경일, 그리고 7장 변경 기록을 같이 고친다. 기능별 세부 형식은 `docs/` 아래 기능 문서에 있다.

### 1.4 용어
| 용어 | 뜻 |
|---|---|
| 사전 질문 | 참석자가 행사 신청서에 적은 궁금한 점 |
| 맞춤 메일 | 사전 질문이나 설문 답에 맞춰 사람마다 다르게 쓴 메일 |
| 매니저 | 이음러닝 마케팅 매니저(정하람). 초안을 검토하고 고친다 |
| 본부장 | 이음러닝 마케팅본부장(한서윤). 메일 발송을 승인하고, 메일은 본부장 이름으로 나간다 |
| 담당자 | 교육컨설팅팀. AI가 답하지 않는 질문에 답한다 (지금은 시연용 가상 명단) |
| 영업 담당 | 산업군별 영업 직원 (지금은 시연용 가상 명단) |
| 수신 동의 | 참석자가 홍보 메일을 받겠다고 동의했는지 (Y/N) |
| 갈래 | 출석자를 어떤 연락으로 보낼지 나눈 것. SALES = 영업 담당이 상담 / ARTICLE = 우리 블로그 글로 답 / STAFF = 담당자 확인 필요 / CUSTOM_TOPIC = 설문에 적은 관심 주제로 글 1편 / THANKS_ONLY = 감사 메일만 |
| 답변 재료 | 질문 유형마다 미리 써 두고 본부장이 승인한 짧은 답변 (`answer_bank.json`) |
| 약속 | 메일에 적은 "○○ 매니저가 ○월 ○일까지 연락(답변)드리겠습니다" |
| 모의 발송 | 실제로 메일을 보내지 않고, 보낸 것처럼 상태만 바꾸는 것 |
| 산업군 | 고객 회사가 어떤 업종인지 (제조업, 금융업 등). 정부 표준 분류(KSIC)를 쓴다 |
| 확신도 | AI가 자기 분류에 얼마나 자신 있는지 0~1로 낸 값 |
| 회신 | 고객이 우리 메일에 보낸 답. 우리가 그 회신에 다시 보내는 메일은 '답장'이라고 부른다 |
| 회신 분류 | 고객 회신을 나누는 7가지. AUTO_REPLY 부재중 자동 응답 / UNSUBSCRIBE 수신 거부 / SALES 견적·도입 상담 / MATERIAL 자료 요청 / STAFF 담당자 확인 필요 / FACT 일정·장소 같은 사실 문의 / THANKS_ONLY 감사 인사만 |
| 블라인드 테스트 | 규칙을 만들 때 보지 않은 데이터로 정확도를 재는 것. 본 데이터로 재면 점수가 부풀려진다 |
| 영업일 3일 | 주말·공휴일을 빼고 3일 |
| 기준일 | 시스템이 '오늘'로 보는 날짜. 평소엔 실제 오늘이고, 시연·테스트에서는 과거 날짜(예: 행사 다음 날)로 바꿔 쓴다 (U07) |

## 2. 배경

### 2.1 문제
> 이음러닝 마케팅팀은 행사 뒤 연락 약속을 **담당자 기억과 메신저에만 의존해** 챙긴다.
> 그래서 참석자의 **10%만** 2주 안에 개별 연락을 받고, 감사 메일도 **평균 행사 4일 뒤에야 나가거나 아예 빠진다.**
> 보내는 메일도 질문과 상관없는 **모두 같은 메일**이다.
> 결국 **계약으로 이어질 수 있던 고객을 놓친다.**

| 무엇이 문제인가 | 실제로 확인된 내용 | 출처 |
|---|---|---|
| 개별 연락 | 행사 후 2주 안에 개별 연락을 받는 참석자 10% | RFP |
| 감사 메일 | 평균 행사 4일 뒤 발송, 행사 6건 중 2건 미발송 | RFP |
| 약속 관리 | 약속이 담당자 기억과 메신저에만 있고, 다음 행사 준비가 시작되면 떠올릴 계기가 사라짐 | 인터뷰 3 |
| 약속 미이행 | 행사 후 개별 연락 약속의 절반 이상이 지켜지지 않음 | RFP |
| 모두 같은 메일 | 참석자의 질문이나 회사에 따라 메일 내용을 바꾼 적 없음 | 과거 발송 문안 메모 |
| 놓친 영업 | 연락을 약속하고 3주 뒤 연락했더니 이미 다른 회사와 계약함 | 07-4 |
| 영업·성과 | 누구를 영업팀에 넘길지 기준이 없고, 어느 행사에서 문의가 나왔는지 세지 않음 | RFP |

> 위 숫자는 과제 원본 자료(RFP, 07)와 대조했다.

### 2.2 사용자
| 구분 | 누구 | 시스템에서 하는 일 |
|---|---|---|
| 쓰는 사람 | 매니저 | 참석자 명단·설문 올리기, AI 초안을 먼저 읽고 고친 뒤 '검토 완료'로 본부장에게 넘기기 |
| 쓰는 사람 | 본부장 | 모든 메일 발송 승인, 답변 재료 승인 |

| 쓰는 사람 | 담당자 | 넘겨받은 질문 확인, 답한 뒤 '답변 완료' 표시 |
| 받는 사람 | 행사 참석자 | 감사 메일·맞춤 메일·정기 발송 수신. 수신 동의에 따라 받는 내용이 다름 |

## 3. 기능 요구사항

시스템이 **해야 하는 일**이다. 업무 흐름별로 나눴다.

### A. 행사별 후속 관리

행사 하나가 끝난 뒤의 일이다. 감사 메일 → 질문 분류 → 맞춤 메일 작성 → 자동 검사 → 승인 → 약속 확인 순서로 진행된다.

| ID | 구분 | 요구사항 | 출처 | 우선순위 | 검증 기준 | 상태 | 변경일 |
|---|---|---|---|---|---|---|---|
| REQ-A01 | 감사 메일 | 각 행사 참석자 전원에게 수신 동의와 상관없이 행사마다 한 통씩 감사 메일 초안을 만든다. 테스트 행사(E07)는 제외한다. | 인터뷰 5·7 | 필수 | 행사별 감사 메일 수 = 그 행사 참석자 수, E07은 0통 | 최초 | 2026-11-27 |
| REQ-A02 | 감사 메일 | 감사 메일 발송 기한은 행사 다음 날 12:00이다. | 인터뷰 7 | 필수 | 모든 감사 메일의 기한 = 행사일 + 1일 12:00이고, 화면에도 예약 시각이 아닌 이 기한이 보임 | 최초 | 2026-11-27 |
| REQ-A03 | 감사 메일 | 현장에서 이메일을 적고 설문에 응답한 사람은 설문 요청 대신 응답 감사 문단을 받는다. 그 외에는 설문 요청 문단에 "이미 응답하셨다면 넘어가셔도 됩니다."를 둔다. | 인터뷰 7 | 필수 | 현장 응답자 메일에 설문 링크 요청 문단 없음 | 최초 | 2026-11-27 |
| REQ-A04 | 감사 메일 | 감사 메일에는 사전 질문 답이나 관심 글을 넣지 않는다. | 인터뷰 7·8 | 필수 | 감사 메일 본문에 질문 답·추천 글 없음 | 최초 | 2026-11-27 |
| REQ-A05 | 분류 | 출석자마다 "답의 재료가 어디 있나"로 갈래를 정한다. 위에서부터 먼저 해당하는 것으로 정한다.<br>① 설문에서 연락 희망·도입 검토를 골랐거나, 사전 질문이 상대 회사 정보가 필요하거나 도입·비용을 물음 → SALES (영업 담당, S01)<br>② 사전 질문을 우리 글·기록으로 답할 수 있음 → ARTICLE (글로 답)<br>③ 사전 질문의 답이 어디에도 없거나 애매·민감 → STAFF (담당자)<br>④ 질문은 없지만 설문에 듣고 싶은 주제를 적은 수신 동의자 → CUSTOM_TOPIC (그 주제 글 1편)<br>⑤ 그 외 (아무것도 안 남겼거나, 질문 없는 미동의자) → THANKS_ONLY (감사 메일만) | 인터뷰 10, 팀 | 필수 | 테스트 질문의 갈래가 정답과 일치 (측정 방법은 REQ-Q02) | 최초 | 2026-11-27 |
| REQ-A06 | 분류 | 질문 사전(규칙 19개)을 먼저 적용하고, 맞지 않으면 AI가 분류한다. AI 확신도 0.6 미만은 STAFF로 보낸다. | 팀 | 필수 | 확신도 0.59 질문이 STAFF로 감 | 최초 | 2026-11-27 |
| REQ-A07 | 메일 작성 | 맞춤 메일은 템플릿이 사실과 약속(담당자 이름, 날짜, 글 제목)을 쥐고 AI는 연결 문장만 쓴다. AI 문장에 숫자·사실이 지어져 있으면 템플릿 문장으로 바꾼다.<br>약속 날짜와 담당자는 본문이 아니라 **별도 칸**에서만 고치고, 본문은 그 칸의 값으로 다시 채운다. 등록되는 약속(A16 ②)은 승인된 칸의 값이다. 누가 이 칸을 고칠 수 있는지는 고객 확인이 필요하다(5장). | 멘토, 팀 | 필수 | 담당자 이름·날짜·글 제목이 칸의 값과 일치, 칸을 고치면 본문도 같이 바뀜 | 최초 | 2026-11-27 |
| REQ-A08 | 메일 작성 | 답변 재료는 근거가 있고 본부장이 승인(approved)한 것만 메일에 넣는다. | 인터뷰 6, 팀 | 필수 | draft 상태 답변이 들어간 메일 0통 (미리보기 옵션 제외) | 최초 | 2026-11-27 |

| 본부장 승인 전에 매니저 검토를 꼭 거쳐야 하는지 (현직자 확인) | A14 |
| 승인이 늦어 약속 날짜가 지났을 때 매니저가 약속 칸을 고쳐도 되는지, 담당자 확인을 먼저 받아야 하는지 (현직자 확인) | A07, A12, A16 |
| 본부장 승인과 동시에 발송할지, 매니저가 따로 발송을 누를지 (현직자 확인) | A14 |
| '연락 완료' 때 연락 방법(전화 / 메일 / 미팅)도 고르게 할지 (운영 논의) | S04 |
